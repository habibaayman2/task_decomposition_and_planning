# memory/ — Person 1 (Memory Systems Lead)

Real IronBridge gap this closes: site engineers and approvers re-explain
the same project context every session — a supplier's known lead-time
pattern, a Project Manager's standing escalation preference, a
recurring low-stock material — because nothing persists past the MCP
connection closing. Forgetting these costs real re-work (a PM escalated
late because the assistant didn't remember they always escalate early),
and a stale, unversioned "fact" costs worse (approving against a lead
time that changed months ago). That's the justification for every
concern below.

This isn't hypothetical for this repo specifically: `db/seed.sql`
already ships **Reinforcement Steel 12mm (MaterialID 2)** sitting below
`MinimumStockLevel` as a deliberate edge case, and **Ironbridge Steel
Yard (SupplierID 2)** as the real steel supplier — exactly the
recurring-low-stock / supplier-behavior scenario memory needs to track.
The demo below uses these real entities, not invented ones.

## Where each rubric concern lives

| Concern | File | What to look at |
|---|---|---|
| Short-term buffer + scratchpad | `short_term.py` | `ShortTermBuffer` (rolling, evicts oldest) vs. `Scratchpad` (separate dataclass, untouched by eviction) — see `demo.py` §1 for proof pruning doesn't wipe it |
| Promote-or-drop routing | `router.py` | `PromoteOrDropRouter.route()` — logged `RoutingDecision` per item, writes only to `EpisodicStore` (never `SemanticStore`) |
| Semantic consolidation | `consolidation.py` | `ConsolidationJob.run()` — separate periodic pass over `EpisodicStore.unconsolidated()`, never called from `router.py` |
| Update / versioning | `stores.py: SemanticStore.write_new_version()` | Old fact flips to `status='superseded'`, new row gets `version+1` — never overwritten in place |
| Expiration | `stores.py: SemanticStore.expire_stale()` | Called each consolidation run; `status='expired'`, distinct from `'superseded'` |
| Conflict resolution | `consolidation.py: ConsolidationJob.run()` | Real conflict demoed: Ironbridge Steel Yard's lead time 14→21 days after a fleet change; `conflict_note` records both values and the resolution rule |
| Self-RAG-style check (memory side) | `self_rag_check.py: SelfRAGChecker` | `relevance_check` / `support_check` / `filter_relevant()` — dropped items are printed/logged, not silently included |

## Storage

`memory/stores.py` creates `memory/memory_store.db` (SQLite) on first
use — a new file, separate from `db/procurement.db`, because episodic/
semantic memory is agent-internal state, not IronBridge business data.
Same lightweight-SQLite convention as `mcp_server/db.py` uses for the
real business data, so it's not a new pattern to learn.
**`memory/memory_store.db` should be added to `.gitignore`** — it's
runtime state generated by running the demo/agent, not source (the repo's
existing `.gitignore` already ignores `db.sqlite3` by name but not this
file — add a line for it, don't rely on the existing pattern matching it).

## Running the demo

```bash
cd <repo root>
python -m memory.demo
```

Resets `memory/memory_store.db` and walks through, in order:
1. Buffer overflow with the scratchpad printed before/after — unchanged.
2. Router decisions for 4 evicted turns (3 forget, 1 episodic), each with
   its logged reason.
3. Consolidation run: writes a new fact for Ironbridge Steel Yard's lead
   time, then a second run detects and resolves a real conflict (14→21
   days, old value preserved not deleted), then a forced-short-TTL sweep
   expiring the stale fact.
4. `SelfRAGChecker` dropping a planted irrelevant recalled item before
   it would reach the agent's context.

## What's a stand-in here, worth flagging like the rest of the repo does

- Fact extraction (`consolidation.py: EXTRACTION_RULES`) is regex-based
  for auditability in a lab demo. Production would swap this for an LLM
  extraction call — the versioning/conflict/expiration logic downstream
  doesn't change.
- `SelfRAGChecker` uses lexical token overlap, not a real LLM critique
  call, for the same zero-dependency-and-inspectable reason. Swap
  `_overlap_score` for a prompted grading call if the team wants a
  stronger checker; `CheckResult` stays the same shape either way.
- Consolidation's conflict rule is "most recent episode wins." That's a
  defensible default, not the only valid one — flag this in the README's
  problem-framing section if the team wants a fancier resolution policy
  (e.g. confidence-weighted, or requiring a second corroborating episode
  before superseding).
- `agent/agent.py` currently tracks no `session_id`/`project_id` at all;
  `INTEGRATION.md`'s patch adds a `session_id` per `run_agent()` call and
  extracts `project_id` best-effort from tool-call arguments. This is a
  reasonable first cut, not a guarantee every turn gets tagged with the
  right project — flag if the team wants stricter project scoping.
